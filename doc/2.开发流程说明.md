## 项目概述

**企业开发脚手架**是一套面向中后台管理系统的通用基础框架，内置 RBAC 权限体系、代码生成、系统监控等能力，业务团队可在此基础上快速扩展业务模块。

### 核心模块

| 模块 | 说明 |
|------|------|
| 首页 | 数据统计、访问趋势、系统公告、快捷入口 |
| 系统管理 | 用户、角色、菜单、部门、日志管理 |
| 代码生成 | 基于数据库表自动生成 CRUD 代码 |
| 文件管理 | 文件上传、下载、预览 |
| API 管理 | 接口文档、在线调试 |
| 系统监控 | CPU / 内存 / 磁盘 / 进程监控 |
| 业务管理 | 业务模块扩展区（按需开发） |

## 分支管理

采用 **Git Flow 简化版**：

```
main          ← 生产环境，只接受 release / hotfix 合并
  └── develop ← 开发主分支，日常集成
        ├── feature/xxx   ← 功能开发
        ├── bugfix/xxx    ← Bug 修复
        └── release/x.x.x ← 发布准备
```

### 分支命名规范

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能 | `feature/模块-功能描述` | `feature/system-user-export` |
| 修复 | `bugfix/问题描述` | `bugfix/login-token-expire` |
| 发布 | `release/版本号` | `release/1.2.0` |
| 热修复 | `hotfix/问题描述` | `hotfix/security-xss` |

### 分支操作示例

```bash
# 从 develop 创建功能分支
git checkout develop
git pull origin develop
git checkout -b feature/business-order

# 开发完成后合并回 develop
git checkout develop
git merge --no-ff feature/business-order
git push origin develop

# 删除本地功能分支
git branch -d feature/business-order
```

## 开发流程

### 整体流程

```
需求评审 → 数据库设计 → API 设计 → 后端开发 → 前端开发 → 联调测试 → Code Review → 合并发布
```

### 详细步骤

#### Step 1：需求评审

- 确认功能范围、验收标准
- 评估是否可复用脚手架现有模块（用户/角色/菜单等）
- 输出：需求文档或 Issue

#### Step 2：数据库设计

- 在 `backend/src/main/resources/db/` 编写 DDL 脚本
- 遵循命名规范（见 [4.数据库脚本设计.md](./4.数据库脚本设计.md)）
- 提交 PR 由 DBA / 架构师 Review

#### Step 3：API 设计

- 在 Knife4j / Apifox 中定义接口契约
- 遵循 RESTful 规范（见 [5.API 接口设计.md](./5.API 接口设计.md)）
- 前后端基于接口文档并行开发

#### Step 4：后端开发

**方式 A：代码生成（推荐，标准 CRUD）**

```
1. 在「代码生成」模块导入数据表
2. 配置包名、模块名、作者
3. 预览并生成 Controller / Service / Mapper / Vue 页面
4. 按需调整业务逻辑
```

**方式 B：手动开发（复杂业务）**

```
1. 创建 Entity → Mapper → Service → Controller
2. 编写单元测试
3. 更新接口文档
```

#### Step 5：前端开发

- 生成或手动创建 `views/` 页面
- 配置路由和菜单权限
- 对接 API，完成交互逻辑

#### Step 6：联调测试

- 前后端本地联调
- 执行测试用例（见 [8.测试项目.md](./8.测试项目.md)）
- 修复 Bug 并回归

#### Step 7：Code Review & 合并

- 提交 Pull Request 到 `develop`
- 至少 1 人 Review 通过后合并

#### Step 8：发布

- 从 `develop` 切 `release/x.x.x` 分支
- 测试通过后合并到 `main` 并打 Tag
- 部署上线（见 [9.部署上线.md](./9.部署上线.md)）

## 提交规范

采用 [Conventional Commits](https://www.conventionalcommits.org/) 规范：

```
<type>(<scope>): <subject>

[body]

[footer]
```

### Type 类型

| Type | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档变更 |
| `style` | 代码格式（不影响逻辑） |
| `refactor` | 重构 |
| `test` | 测试相关 |
| `chore` | 构建/工具变更 |

### 示例

```bash
feat(system): 新增用户批量导入功能

- 支持 Excel 模板下载
- 支持 xlsx 文件上传解析
- 导入结果反馈成功/失败条数

Closes #123
```

```bash
fix(auth): 修复 Token 过期后未跳转登录页的问题
```

## Code Review 流程

### Review 检查清单

**功能性**
- [ ] 功能是否符合需求描述
- [ ] 边界条件是否处理（空值、超长、并发）
- [ ] 权限控制是否正确

**代码质量**
- [ ] 命名是否清晰、符合规范
- [ ] 是否有重复代码可抽取
- [ ] 异常处理是否完善
- [ ] SQL 是否有性能问题（N+1、全表扫描）

**安全性**
- [ ] 接口是否有权限注解
- [ ] 输入是否校验（XSS、SQL 注入）
- [ ] 敏感信息是否脱敏

**测试**
- [ ] 是否有对应单元测试
- [ ] 核心路径是否覆盖

### Review 时效

- 普通 PR：24 小时内完成 Review
- 紧急 Hotfix：4 小时内完成 Review

## 版本发布流程

### 版本号规则

采用语义化版本 `MAJOR.MINOR.PATCH`：

| 变更类型 | 版本位 | 示例 |
|----------|--------|------|
| 不兼容变更 | MAJOR | 1.0.0 → 2.0.0 |
| 新功能（兼容） | MINOR | 1.0.0 → 1.1.0 |
| Bug 修复 | PATCH | 1.0.0 → 1.0.1 |

### 发布步骤

```bash
# 1. 从 develop 创建 release 分支
git checkout develop
git pull
git checkout -b release/1.1.0

# 2. 更新版本号、CHANGELOG
# 3. 测试验证

# 4. 合并到 main 并打 Tag
git checkout main
git merge --no-ff release/1.1.0
git tag -a v1.1.0 -m "Release v1.1.0"
git push origin main --tags

# 5. 合并回 develop
git checkout develop
git merge --no-ff release/1.1.0
git push origin develop

# 6. 删除 release 分支
git branch -d release/1.1.0
```

### CHANGELOG 格式

```markdown
## [1.1.0] - 2026-09-16

### Added
- 用户管理支持 Excel 批量导入
- 系统监控新增进程列表

### Fixed
- 修复菜单树展开状态丢失问题

### Changed
- 优化首页加载性能
```
